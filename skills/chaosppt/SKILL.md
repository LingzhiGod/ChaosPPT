# ChaosPPT

Author new decks as explicit controls in HTML/CSS, not arbitrary inferred DOM. HTML remains the layout/preview source; declared control boundaries are the PPT editing boundaries. Read [the controls contract](references/controls.md) before writing a new page. Legacy decks remain supported for migration; do not create new unmarked decks.

## Theme-first design workflow — default recommendation

Read [the design workflow](references/design-workflow.md) before designing any new slide. Resolve the audience and content goals, then establish the aesthetic direction, background policy, full palette and typography hierarchy **before** authoring page visuals. Record concrete decisions in the deck's `design-spec.md` and implement them in shared `theme.css`/masters. Existing decks inherit their confirmed theme unless the user requests a redesign.

- Define font family, size, weight, line height and color for cover titles, page titles, section/subsection headings, body text, chart labels, captions and footers. A role has one consistent treatment across pages; different heading levels do not need different colors.
- Default to one background treatment across the deck. Any background variants must belong to the same palette and be assigned to specific page roles in the design spec before use. Do not alternate dark/light pages or invent new colors merely for variety.
- Establish grid/safe margins, spacing, image/icon treatment, corner/line style and chart semantic colors as part of the same aesthetic system. Use shared tokens, not independent per-slide styling.
- Validate the system on representative pages before expanding the full deck. Change shared tokens and recheck affected pages when revising the theme. Specific user/brand/template requirements override these defaults; do not add an unnecessary approval checkpoint when reasonable design choices are available.

## General presentation design — always apply

Read [the design principles](references/design-principles.md) before planning layouts or choosing charts. Apply these defaults to every deck, together with the user's brand, template and audience requirements.

- Establish one deck-wide visual system in shared `theme.css` and masters: font roles and size hierarchy, palette, spacing/grid, safe margins, graphic treatments and chart styles. Keep the same entity/status mapped to the same color, label and unit across pages. Use only the background variants predeclared in the design spec; otherwise keep the common background treatment.
- Give each page one clear information goal and visual focus. Use hierarchy, contrast, alignment, proximity, repetition and whitespace to guide reading. Reorganize or split crowded content while maintaining readable text and chart labels.
- Choose visuals by the audience's analytical task: comparisons/rankings → bars or dots; trends → lines; composition → part-to-whole charts; distributions → histograms/box plots; relationships → scatter; exact lookup → tables; processes/hierarchies → diagrams. Check the selection guide for prerequisites and exceptions before implementation.
- Match visual encodings to evidence. Preserve denominators, units, periods, category order, missing values and negative values. Keep comparable axes/scales consistent; use zero-based bar lengths. Pair semantic colors with labels or shapes. Use decorative elements to reinforce the message and support legibility.
- Review both individual slides and the deck as a sequence before export: theme consistency, narrative flow, readable hierarchy, correct visual selection, truthful scales and useful labels. Follow the copy rules during that review. Rendering diagnostics provide layout measurements; the Agent performs the design review.

## Presentation copy style — always apply

Write for the audience's question and the strongest supported message. Read [the copy rules](references/copy-style.md) before drafting or revising visible slide text; they apply to every deck without a separate skill invocation.

- Do not append sentence-ending periods to slide titles, headings, labels, bullets, captions or standalone short statements by default, even when a short statement is grammatically complete. Use normal punctuation for continuous prose when needed; preserve exact quotations, user-required punctuation, decimals, abbreviations and URLs. Apply the punctuation rules in the copy reference during final review.
- Keep authoring housekeeping out of titles, footers, badges, captions and tiny text. Do not add “待测”“待补充”“真实材料待补充”“数据待核实”“仅供参考”“以实际为准” or equivalent English disclaimers to compensate for missing input or unperformed checks.
- When evidence is missing, omit the unsupported metric/chart, narrow the claim, or use a factual qualitative explanation. Record production questions in `notes` or the handoff, away from the slide canvas. Never fabricate evidence or present synthetic numbers as measured results.
- Keep audience-relevant facts: requested test-plan statuses, decision-critical limitations, exact quotations, real citations, and a concise forecast/sample-data label when needed to interpret the content. State these once in ordinary readable content, with their actual scope.
- Before export, review **all visible copy**, including master footers, SVG text and Canvas labels. Remove unsolicited drafting reminders and self-protective fine print; shortening, shrinking, fading or moving them to another visible corner does not resolve the issue. Keep only text that advances the page's message or supplies necessary interpretation.

## Start

Resolve this skill's directory and call `node <skill-dir>/scripts/run.mjs --help`. The runner uses the bundled engine when installed, or the repository engine during development. Read [the engine reference](references/engine.md) before authoring; it defines the actual manifest and async APIs. Never guess a readiness API.

1. Map the user's materials to ordered pages, each with a purpose, sources and a visual choice justified by its information goal. Preserve supplied facts and follow the copy rules when handling gaps or synthetic data. Confirm only material missing requirements.
2. `init` an empty project directory. Before designing the first slide, complete the theme-first workflow: record the aesthetic direction, background/palette and full typography-role table in `design-spec.md`, then implement the values in shared `theme.css`/masters. Set supported `deck.json` fields for size, fonts, theme, masters and ordered slide IDs; do not invent new manifest fields for the design spec. Use local resources; remote access is off by default.
3. Design representative pages before the full deck. Use Grid/Flex in unpainted layout containers and declare every visible object as text, shape, image, group, media or raster. Put an entire paragraph in one text control with inline rich text and br; use real group controls for components. Arbitrary Canvas/SVG/HTML is allowed only inside an explicitly declared raster control, never as an unmarked fallback. Apply the shared design principles and chart selection guide; vary compositions to fit the content while retaining the deck's visual identity. Use `data-element-id` on important elements.
4. Register asynchronous data/chart work immediately using `ChaosPPT.waitUntil(promise)`. Await fonts before drawing Canvas text. Use `onCapture` for a deterministic static state; stop application-owned animation loops there.
5. Run `inspect --json`, fix errors, then `render`. Review every generated PNG using the design and copy checklists; inspect Chinese glyphs, long titles, chart labels and clipping. Compare all pages together against `design-spec.md` for background, heading-font/size/color, body typography, palette and layout consistency, using a thumbnail overview when useful. Diagnostics are heuristic, not a visual-quality verdict. Prefer reorganizing text to shrinking it below readable size. Use `data-allow-overflow` only for intentional decorations, never to hide content errors.
6. For new explicit-control decks, pass `--pptx-mode editable` to get 1:1 native controls and real groups. Choose `--pptx-mode compatible` when the user prioritizes screenshot fidelity. The CLI default stays compatible for backward compatibility, so always state the choice. Run `export --format pdf,pptx` with that choice, then `verify`. For editable output read `dist/conversion.json`, check fallback reasons and font requirements, and inspect the actual PPTX rendered in a presentation application; reference PNGs are not previews of the native PPTX. Export blocks on errors. The `dist` directory is generated and replaced on successful builds; keep user sources elsewhere.
7. Deliver source project plus requested outputs. Explain the chosen export mode. Compatible mode uses image backgrounds; editable mode maps supported elements to native objects and keeps complex content as images. Both keep notes and explicitly marked MP4/GIF as native media. Explicit text controls are single rich-text frames; group controls are native PPT groups. Only legacy unmarked HTML uses fragmented visual-line inference. Unsupported explicit controls fail with CONTROL_INVALID; fix the declaration or deliberately use raster instead of silently flattening. Target fonts must be installed; the exporter does not embed fonts. Do not claim 95% editability from the DOM text statistics. For media authoring, read the embedding section of the engine reference and supply local MP4 posters. PDF defaults to browser text/vector output; use raster mode when requested for screenshot fidelity. Inspect PDF pages too; structural verification alone does not prove visual equivalence. Claim PowerPoint compatibility testing only if actually performed.

The runtime supports fixed canvases, browser layout, local fonts, masters, preview fade transitions, static PDF/PNG, and native MP4/GIF embedding in PPTX. It does not automatically paginate arbitrary HTML or convert HTML animations to PPTX transitions.
